## Findings (ranked)

1. **MEDIUM: an order can move another workspace's stock.** `supabase/migrations/00029_stock_swap_insert.sql:34-37,55-57`
   - Failure: `orders.product_id` only references `products(id)`, so nothing checks that the product is in the same workspace. The `security definer` trigger writes a movement for whatever product id the order holds.
   - Reproduced in a rolled-back transaction. A W1 admin ran `update orders set confirmation_status='confirmed', product_id=<W2 product>`. That wrote a `-2 order_stock_sync` row with `workspace_id=W1`, and the stock of the W2 product went to -2. W2 cannot see the row.
   - The UPDATE path already had this hole in 00018. This branch adds the INSERT path and the old-product release.
   - Fix, either:
     - a composite FK `orders(workspace_id, product_id) -> products(workspace_id, id)`. This needs `unique(workspace_id, id)` on products and a check of existing rows, so it is a schema decision for the owner;
     - or, in the trigger, raise an exception when the product's `workspace_id` is not the order's `workspace_id`.
   - Add an RLS test.

2. **MEDIUM: DB.md describes 00028, not the code that runs.** `docs/DB.md:58,82`
