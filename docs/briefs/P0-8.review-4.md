## Findings (ranked)

### 1. MEDIUM (needs a decision extending D29): ZR sync moves a swapped order out of `swap` and deducts its stock again
- Where: `supabase/migrations/00027_zr_state_sync.sql:63-65` (`apply_zr_state` overwrites any `delivery_status`) together with the reconcile target at `supabase/migrations/00030_stock_workspace_guard.sql:54-56`.
- Failure:
  - Order A is `returning` with a ZR parcel, and the map has `retour_en_cours -> returning`.
  - `swap_order(A)` leaves stock unchanged (141): A releases its unit and B holds one.
  - A newer ZR event sets A from `swap` back to `returning`. A is held again, stock drops to 140, and the item is counted twice.
  - A later `livre`/`encaisse` event (-> `delivered`) has the same effect.
  - This breaks D29's "a swapped item is counted once". Swapping from `returning` is allowed by `src/app/app/orders/swap-card.tsx:12`, and the old 00018 trigger did not move stock on swap -> X.
- Fix (choose one):
  - (a) target = 0 whenever `swapped_to_order_id is not null`, and add that column to the early-return change check.
  - (b) `apply_zr_state` skips orders whose status is `swap`.

### 2. MEDIUM: `swap_order` has no precondition, so a double submit deducts twice
- Where: `supabase/migrations/00030_stock_workspace_guard.sql:104-118`.
- Failure:
  - Calling `swap_order(A)` twice (double click, two tabs or a retry) creates B1 and B2, each holding -qty. Stock goes from 142 to 140.
  - A links only to B2, so B1 is an orphan that still holds stock.
  - The `FOR UPDATE` lock serialises the two calls, but A is not re-checked once the lock is taken.
- Fix:
  - After the lock, `raise` if `a.swapped_to_order_id is not null or a.delivery_status = 'swap'`.
  - Enforce the swappable delivery statuses on the server, not only in the UI.

### 3. LOW (owner: role permission, D28): admins can UPDATE or DELETE `stock_movements`
- Where: `supabase/migrations/00003_products.sql:173-177` (`stock_movements_adm` covers all commands).
- Failure:
  - Deleting or editing an `order_confirmed` row through PostgREST leaves `products.stock` unchanged, because the trigger only fires on insert.
  - The next reconcile then deducts again.
- Fix: limit authenticated users to select and insert, or add update and delete triggers.

### 4. LOW: `swap_order` accepts a `p_customer_id` from any workspace
- Where: `supabase/migrations/00030_stock_workspace_guard.sql:111-113`.
- Failure:
  - The foreign key only checks that the customer exists, so B can be linked to another workspace's customer.
  - No data exposed was found, because RLS hides that customer. Direct order inserts have the same gap.
- Fix: check `customers.workspace_id = a.workspace_id`.

### 5. LOW (already in the backlog): deleting order B leaves stock deducted
- A's `swapped_to_order_id` is set to null, and B's movements are orphaned with `order_id = null`, so the stock is never given back.
