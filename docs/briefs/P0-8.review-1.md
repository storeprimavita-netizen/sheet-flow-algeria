## Findings (ranked)

1. **HIGH: reopening a returned order deducts stock twice** (`supabase/migrations/00028_stock_return_undo.sql:28-34`)
   Branch 4 ignores `confirmation_status`, and branch 3 skips any order whose old delivery status is `returned`.
   Repro (rolled-back transaction):
   - confirm, then delivered, then returned (net 0);
   - admin sets `confirmation_status='wait_for_confirmation', delivery_status='wait_for_deposit'` in one update (allowed by `transition_order_status`);
   - only the undo is written, so net is -1 although nothing is confirmed;
   - re-confirming gives net -2 for 1 unit.

   This flow ended at the correct -1 before P0-8, so it is a regression. The result also depends on whether the delivery or the confirmation change comes first.
   Fix: reconcile instead of firing per event. Target net = `-quantity` if confirmed and delivery is not returned, else 0. Insert `target - current_net` when it is not zero. Minimum fix: branch 4 requires `new.confirmation_status = 'confirmed'`.

2. **MEDIUM (owner decision): returned -> `cancelled` treated as the parcel leaving again** (same lines)
   Confirm, then returned, then cancelled gives net -1 while the item is physically in the warehouse. The brief said to ask the owner if `cancelled` exists in the enum. It does, and the owner was not asked.
   Fix: get the owner's call. If cancelled should keep the restock, add `and new.delivery_status <> 'cancelled'`.

3. **MEDIUM: live test files collide on the same order** (`src/lib/stock-return.test.ts:35`, `src/lib/integrations/zrexpress-sync.test.ts:69`)
   Both files pick an order with `limit(1)` and no ordering, and both land on the same order. Vitest runs files in parallel, and each file's `reset()` deletes the other's movements. This caused 2 ZR test failures in 1 of 3 runs, so the gate is flaky.
   Fix: each test file inserts its own product and order and deletes them afterwards.

4. **LOW: ZR test cleanup is incomplete** (`zrexpress-sync.test.ts:56,77`)
   Cleanup deletes only `order_returned` rows, so every run leaves an `order_return_undone` row behind, which skews the net guard for that order on later runs.
   Deleting movements also never reverses `products.stock` (the stock trigger only reacts to inserts). The seed product's stock drifted from 154 to 159.

5. **LOW: no index for the new count** (`stock_movements`)
   There is no `order_id` index, so the new count scans the whole table on each exit from `returned`.
   Fix: add an index on `(order_id, reason)`.

6. **LOW: undo uses the current product and quantity** (00028)
   Branch 4 uses `new.product_id` / `new.quantity`. If an admin changes either while the order is returned, the undo hits a different product or amount than the return did. The older branches have the same weakness.

7. **LOW: dead assertion** (`stock-return.test.ts:77`)
   `expect(start).toBeDefined()` checks nothing, and `start` is never used. Assert the actual stock delta instead.
