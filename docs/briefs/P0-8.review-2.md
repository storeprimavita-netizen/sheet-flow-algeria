## Findings (ranked)

### H1 (high, owner decision): swap flow deducts stock twice
- `supabase/migrations/00028_stock_return_undo.sql:32-34`, `src/app/app/orders/actions.ts:428-490`.
- The brief's claim of "no exchange/swap values" is wrong: 00016 adds `exchange` and `swap`. `swapOrder` inserts order B already `confirmed` (the trigger is AFTER UPDATE only, so B holds nothing yet), then sets A to `swap`.
- D25 target treats `swap` as holding stock. Repro: A confirmed -> delivered -> returned (net 0). Insert B confirmed, set A to swap: net -qty. Any later update of B (e.g. shipping it): net **-2qty** for one item. Starting from a delivered A, 00018 gave -qty, so this is a regression.
- Fix (needs a DECISIONS row): add `'swap'` to the "holds nothing" list so stock follows B, and reconcile on AFTER INSERT too, so B deducts when it is created. Decide `exchange` explicitly as well (currently it keeps stock deducted).

### M1 (medium): any update to an old order emits a correcting movement

- Repro: an order delivered before 00018 holds a legacy `delivered` row of -qty. Touching `updated_at` writes another -qty, so net is **-2qty**. Orders that 00018 left out of line with D25 (e.g. confirmed + delivery `cancelled`) get +qty on their next edit. If the owner already fixed them by hand on the stock page, the stock is counted twice.

- Fix: the owner runs a read-only count of drifted orders on the real data. Then either run a one-time reconcile in the migration (reason `order_stock_sync`) or have the trigger skip orders that have legacy rows. Record the choice in DB.md/PROGRESS.
