## Findings (ranked)

### M1 · medium · src/lib/pricing-real.ts:56
- **Failure:** `delivery_pct = counts.delivered / counts.confirmed` mixes two order sets. `delivered` includes swap replacements; `confirmed` does not (`00031_kpi_contract.sql:84` vs `:88`).
- **Reproduced:** one swap with a delivered replacement moved a product from 4/7 to 5/7 with no other change.
- **Impact:** the rate can go above 100%, which inflates the Real scenario's profit. It also breaks D4, which says rates are computed only in SQL.
- **Fix:** add a `delivered_of_confirmed` metric to `kpi_rates`, built on one set, and read it in pricing-real.ts.

### M2 · medium · src/lib/pricing-real.ts:38,47
- **Failure:** `orders30 = set30.length` comes from `rpc("kpi_order_set")`, and PostgREST stops at `max_rows = 1000` (`supabase/config.toml:19`).
- **Impact:** a product with more than 1000 orders in 30 days shows 1000 leads, so `lead_cost_eur` comes out too high.
- **Fix:** count the orders in SQL, either as a count key in the KPI contract or through a scalar RPC.

### M3 · medium · OWNER DECISION · supabase/migrations/00031_kpi_contract.sql:33
- **Failure:** a swap original is removed from the order set entirely, so its return disappears from the numbers.
- **Reproduced (rolled back):** original returned, swapped, replacement delivered. Delivery rate went from 0.80 to 0.833; counting the return would give 0.714.
- **Why it needs the owner:** a returned parcel is raising the rate, which conflicts with D40/D46 ("never an inflated rate"). The owner has to choose one of two options:
  - (a) count the original's carrier outcome from before the swap (for example as returned) in the delivery denominator;
  - (b) accept the current behaviour and record that in D46.

### L1 · low · funnel counts disagree
- **Failure:** `stage_counts.received` and `confirmed` leave replacements out. `shipped` (`00031:398-405`), `per_product.orders_received` (`:497`), `daily` (`:533`) and `pnl.orders_confirmed` include them.
- **Reproduced:** `kpi_summary` gives 11/7 where `pnl_summary` gives 12/8.
- **Impact:** break-even (`pricing.ts`, which uses `pnl.orders_confirmed`) is compared against a delivery rate built on a different set (`dashboard/page.tsx:327`).
- **Fix:** use one rule for replacements in every count.

### L2 · low · src/app/app/dashboard/page.tsx:205-206,243

- **Impact:** swap replacements also inflate "orders today".
- **Fix:** take the order ids from `kpi_order_set`.

### L3 · low · 00031_kpi_contract.sql:322-328, 646-652
- **Failure:** `pnl_by_product` runs the full `kpi_lines` and `pnl_lines` once per product. `product_stats` re-runs `kpi_order_set` inside a LATERAL join for each product.
- **Impact:** 33 ms on 315 orders today, but the cost grows with products × orders (quadratic).
- **Fix:** compute the set once and group it by product.
