## PRODUCT VISION

A complete ERP dashboard for Cash-On-Delivery ecommerce in Algeria. One store/workspace today, but the database and auth must be **SaaS-ready** (the owner plans to sell it to Algerian ecommerce sellers later). Practical rule: every business table carries a `workspace_id`, RLS scopes everything by workspace, and nothing hardcodes "there is only one store."

Stack (fixed): **Next.js (existing app) + Supabase free tier (Postgres, Auth, RLS, Edge Functions) + Vercel** for hosting. Currency: **DZD** everywhere; ad spend and sourcing costs may be entered in **USD or EUR**, converted using rates stored in Settings. No real data migration needed — schema can be clean.

The app must feel like ONE interconnected tool, not many sections. Exactly these areas in the sidebar:

1. **Dashboard** (home, BI)
2. **Orders** (subsections: All / Confirmation / Delivery)
3. **Products**
4. **Finance** (subsections: Overview / Expenses / Ad spend / Income) — admin-only, RLS-enforced
5. **Contacts** (Customers / Suppliers)
6. **Team & Rules** (users, permissions, rules, meetings, tasks, performance, audit log)
7. **Settings**

**Interconnection is a hard requirement, not a nice-to-have.** Records that a user thinks about in two places (product expenses, ad spend, orders, tasks) are created and edited by ONE shared component reachable from every relevant page, with context pre-filled. Every displayed number drills through to the records behind it via URL-encoded filters. Every detail view lists its relations. Income is never typed by hand — it derives from delivered orders. See the UI prompt's interconnection rules.

## USERS, ROLES, PERMISSIONS

- **Admin** (owner): everything. Creates/invites users, assigns roles, sees all finances, manages settings. Currently 2 admin-level users.
- **Confirmation agent**: sees the Orders → Confirmation queue and customer info (including customer risk score and history). Can change confirmation status and write a confirmation comment. CANNOT see product costs, expenses, profits, dashboard finances, or settings.
- **Delivery agent**: sees Orders → Delivery queue. Can change delivery status. Same financial blindness as confirmation agent.
- Enforced by Supabase Auth + a `profiles` table (`role`, `workspace_id`) + **Row Level Security on every table** + UI route guards. RLS is the real wall; UI hiding is cosmetic.
- **Audit log**: every status change, expense entry, and settings change records who/what/when/old→new. Admin-visible page (inside Team & Rules or Settings).

## SECTION SPECS

### 1) Dashboard (BI)

Global filter bar (applies to everything below): date range, product(s), wilaya, source (Shopify / LightFunnels / manual), confirmation agent, delivery agent, status.

- KPI cards: total invested, revenue (delivered orders), net profit, confirmation rate, delivery rate, orders count by stage.
- Funnel: received → confirmed → shipped → delivered (with drop-off %).
- Delivery rate + order count **per wilaya** (table + chart), with a visual flag on wilayas marked "stop shipping".
- Rates **per agent** and **per product**.
- Spending breakdown by expense category (see Products/expenses categories).
- Everything computed from orders + expenses; no manually-entered totals.

### 2) Orders

One `orders` table, three filtered views:

- **All**: every order, every column, full filters.
- **Confirmation**: queue for confirmation agents. Statuses: `wait_for_confirmation`, `no_answer`, `closed_phone`, `cancelled`, `confirmed`. Free-text `confirmation_comment`. Shows customer history + risk score inline while calling.
- **Delivery**: queue for delivery agents. Statuses: `wait_for_deposit`, `bureau_deposited`, `in_transit`, `out_for_delivery`, `stop_desk_waiting`, `delivered`, `cancelled`, `delayed`, `returning`, `returned`. Manual updates only (no carrier API for now — but leave the status model clean enough to bolt a carrier integration on later).

Order fields (minimum): source + external ID, product ref, variant/qty, customer name + phone (normalized) + wilaya + commune/address, sale price, **delivery fee** (comes from Shopify/LightFunnels payload; fallback to the per-wilaya fee table in Settings; admin can override per order), both statuses, comment, timestamps for EVERY status transition (drives agent stats + time-to-confirm), created_by/updated_by.

Behaviors:

- **Webhook ingestion**: Supabase Edge Functions receive Shopify (`orders/create`) and LightFunnels order webhooks. Verify signatures. Map payloads → unified order shape. The user switches between platforms over time, so both stay configured; source is per-order.
- **Duplicate detection**: same normalized phone + same product within 48h ⇒ flag the new order visually and in the confirmation queue (agent decides).
- **Customer auto-creation**: every order upserts a customer contact keyed by normalized phone (see Contacts).
- **Delivered ⇒ income**: a `delivered` order automatically counts as revenue for its product. `returned` orders automatically count the return fee as a product expense (fee from Settings).
- Manual order creation also possible (admin).

### 3) Products

Product list with product status: `to_be_tested`, `tested`, `confirmed`, `cancelled`. Product page (page, not cramped popup) with tabs:

- **Details**: name, images, tissu/fabric, category, variants, sale price, sourcing cost + currency, notes.

- **Statistics** (auto): orders received/confirmed/delivered/returned, confirmation rate, delivery rate, revenue, total expenses by category, allocated share of monthly fixed fees, **net profit**, ad cost per delivered, profit per delivered.

### 4) Contacts

One section, two types, full CRUD:

- **Suppliers/partners**: type ∈ {shooting_studio, atelier_couture, emballage, other}, name, phone(s), location, notes, linked expenses history.
- **Customers**: auto-created from orders (dedup by normalized phone; handle 05/06/07 formats, +213, spaces). Fields: name, phone, wilaya, commune. Auto stats: orders count, confirmed count, delivered count, returned count, **risk score** (simple transparent formula, e.g. based on return/refusal ratio and no-answer history — document the formula in code and docs, keep it tunable in Settings). ## PRICING ENGINE (exact model from the xlsx — do not "improve" the math)

All money in DZD unless noted. `fx` = the DZD rate of the chosen ad currency (USD or EUR, from Settings). Per scenario inputs:

- `product_cost` (DZD per unit), `ad_cost_per_lead_fx` (in USD/EUR), `confirmation_rate` (%), `delivery_rate` (%), `delivery_price` (DZD per delivered order), `confirmation_agent_fee` (DZD/order), `packaging` (DZD/order), `sale_price` (DZD), `daily_ad_spend_fx`, `return_fee` (DZD per returned parcel), monthly fixed fees list (DZD).

Derived (guard every division by zero; show "—" not NaN):

```
ad_cost_per_confirmed = (ad_cost_per_lead_fx * fx) / (confirmation_rate / 100)
ad_cost_per_delivered = ad_cost_per_confirmed / (delivery_rate / 100)
confirmed_per_day     = (daily_ad_spend_fx * fx) / ad_cost_per_confirmed
delivered_per_day     = (daily_ad_spend_fx * fx) / ad_cost_per_delivered
returns_fee_per_delivered = (confirmed_per_day - delivered_per_day) * return_fee / delivered_per_day
fixed_fees_per_day    = sum(monthly_fees) / 30
other_fee_per_delivered = fixed_fees_per_day / delivered_per_day
net_profit_per_delivered = sale_price - (product_cost + ad_cost_per_delivered
                          + delivery_price + confirmation_agent_fee + packaging
                          + returns_fee_per_delivered + other_fee_per_delivered)
net_profit_daily   = net_profit_per_delivered * delivered_per_day
net_profit_monthly = net_profit_daily * 30
```

UI: three scenario columns (Best/Medium/Worst) with all inputs editable and results live, saved per product; a fourth "Real" column auto-computed from actual product data (read-only). Also show per-scenario daily/monthly confirmed & delivered order counts and monthly spend, like the sheet. NEVER show the raw spreadsheet; this is a native, clean calculator. Unit-test the formulas against the sheet's known values (e.g. best scenario in the file: sale 4900, cost 2500, rate 255, lead 2€, conf 65%, del 65%, packaging 50, return fee 100, spend 20€/day, monthly fees 3000+5000 ⇒ net_profit_per_delivered ≈ 1025.94 DZD, monthly ≈ 130,037 DZD).

## DATABASE DIRECTION (the architect finalizes the schema in the plan)

Tables (all with `workspace_id`, `created_at`, `updated_at`; RLS by workspace + role):

`workspaces`, `profiles` (user, role), `products`, `product_scenarios`, `expenses`, `ad_spend_daily`, `orders`, `order_status_history`, `customers`, `contacts` (suppliers), `wilayas_fees`, `fixed_fees`, `exchange_rates`, `settings`, `rules_docs`, `meetings`, `meeting_objectives`, `tasks`, `audit_log`, `integration_configs`, `webhook_events` (raw payload store for debugging/replay), plus **`option_sets` and `options`**.

**Option sets (Notion-style user-extensible taxonomies)**: `option_sets(id, workspace_id, key, label, allows_multi)` and `options(id, workspace_id, set_id, label, color_token, icon, sort_order, archived_at, created_by)`. Used for supplier/atelier type, product category, tissu/fabric, expense subcategory, order tags, cancellation reason, customer tags. Referencing rows store the **option id**, never the label, so a rename propagates retroactively. Seed defaults per workspace. Options are archived, not deleted, and support merge-into-another. **Order/delivery/product/task statuses are NOT option sets** — their keys are fixed because statistics and business logic depend on them (only labels and colors are editable).

Notes: normalized phone as customer key within workspace; status enums as Postgres enums or checked text; status transitions written by trigger or app layer into `order_status_history`; delivered/returned financial effects computed by views/queries, not stored duplicated when avoidable.
